# create-skill

## 考え方

スキル本文は呼び出されるたびにコンテキストに載り、書かれたことはすべて指示として解釈される。
そのため、モデルが自力で判断できることは書かず、書かなければ失敗すること・判断がぶれることだけを書く。
記述が具体的すぎるほど、参照先や運用が変わったときに古い指示が残って誤動作の原因になる。

## 手順

1. 要件を把握する：
  - 会話履歴に対象の作業があれば、そこから手順・使用コマンド・ユーザーの修正指示を抽出する
  - 不明点（目的、呼び出し契機、ユーザー確認のタイミング、外部操作の有無）だけを AskUserQuestion でまとめて確認する
  - 参照するスクリプト・テンプレート・設定ファイルは存在を確認する。中身は把握のために読むが、スキルには書き写さない

2. 以下の「書き方」に従って SKILL.md を書く。既存のスキルは書式の手本にしない

3. 削る：
  - 各行について「消したらモデルの挙動が変わるか」を問い、変わらない行を削除する
  - 依頼にない機能（追加の確認、警告、代替案の生成など）を足していないか確認する。足したいものはスキルに入れず、ユーザーへの提案として伝える
  - MUST・必ず・絶対 などの強調は、実際に失敗が起きた箇所以外から外す

4. SKILL.md の全文を提示し、意図的に省いた内容があれば添える。保存先は `.claude/skills/<name>/SKILL.md`（指定があればそれに従う）

## 書き方

### description

常にコンテキストに載り、呼び出すかどうかの判断材料はこれだけになる。何をするスキルかと、呼び出しの言い回し例を書く。

例：`現在のブランチの変更内容をもとにPull Requestを作成する。「プルリクエストを作成」「PRを作って」などで利用する。`

### 本文

- description に書いたこと（何をするか、いつ使うか）は繰り返さない
- 判断を伴うスキルでは、冒頭に背景にある意図・考え方を短く書く。個々の指示に理由を並べるより、モデルが想定外の状況でも判断できるようになる。手順どおりに実行するだけの操作系スキルには不要
- 手順は「何をするか」を書き、「どうやるか」はモデルに任せる（例：「ベースブランチとの差分を確認する」で足り、git コマンドは不要）
- スクリプト・テンプレートはパスで参照して「読んで従う」と書く。中身・環境変数・内部挙動は説明しない
- 個別の理由は、モデルが誤りやすい指示にだけ付ける（例：「本文は質問 UI に隠れるため preview に入れる」）
- 出力について：
  - 形式が決まっている場合は、プレースホルダーで形式を示す（例：`<タイトル>: <概要>`）
  - トーンや粒度がぶれやすい場合は、具体例を 1 つ載せる
  - どちらでもなければ書かない
- 80 行以内を目安に、必要な分だけ書く

### allowed-tools

スキルが使うツール・コマンドのうち、実行時に権限の確認が求められるもの（スクリプト、独自の CLI、書き込みや外部操作を伴うコマンドなど）だけを必要最小限のパターンで列挙する。確認なしで使えるもの（Read、Grep、`git log` など）は書かない。

例：`allowed-tools: Edit, Bash(gh pr create:*)`

## スキル改善時

- 実際に起きた失敗を起点に、その失敗を防ぐ最小の記述を足す
- 足すと同時に、不要になった記述や重複を削る
