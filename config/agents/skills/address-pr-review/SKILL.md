# Address PR Review

作業前に対応方針とコミット方針をすべて確定させ、作業開始後にユーザーへ確認しないで済むようにする。ユーザーはコメントを GitHub で読み済みのこともあれば未読のこともあり、スレッド内で方針が決まっていることもある。
plan は「何を・どう直し・どのコミットに入れるか」をユーザーが一度で確認・修正できる形にする。plan のレビュー負荷がこのスキルの成否を決めるため、判断が要るものは plan の前に個別に確認し、plan は確定した内容の一覧にする。
コミット方針は作業前に確定させる。後から決めると修正の作り直しが発生する。

## 1. 未解決コメントの取得

`scripts/fetch_unresolved_comments.sh` を実行する。PR 番号の指定があれば第 1 引数に渡す。
未解決コメントがなければその旨を伝えて終了する。

## 2. 調査

各コメントについて、スレッドの議論・該当コード・PR のコミット履歴を確認し、次を決める。

- 対応案（対応する / 対応しない）と具体的な修正内容
- 修正の由来となった既存コミット

スレッド内で合意済みの方針があればそれに従う。

## 3. 判断が要るものとコミット方針を確認

AskUserQuestion で次をまとめて決める。

- 設計判断を含むもの・対応案が複数ありうるもの・レビュアーの意図が読み切れないものの対応方針。迷ったらここで聞く。各質問にはコメントの要点とファイル:行を含め、選択肢には具体的な対応案（対応しない案も含む）を並べる。typo・スタイル修正・スレッドで合意済みのものは聞かない
- コミット方針: 全修正を既存コミットに fixup/amend で統合するか、全修正を新規コミットにするかの 2 択

## 4. Plan Mode で提示

Plan Mode に入り、コミット順に並べた plan を書く。fixup なら PR の既存コミット順、新規なら作成順にする。

```
### <short sha> <subject> | <新規コミットメッセージ案>
- <番号>. <指摘の主旨> (<ファイル:行>) → <何をどう変えるか>

## 対応しない
- <番号>. <指摘の主旨> → <理由 1 行>
```

- 番号は通しで振り、ユーザーが「3 は対応しない」「5 は 2 のコミットに含めて」のように番号で指示できるようにする
- plan は読み手が会話を見ていない前提で書く。調査の経緯、方針を決めた理由の長い説明、スキルの手順への言及は書かない

ユーザーの修正指示があれば plan を更新して再提示する。

## 5. 修正

承認された plan に従って修正する。独立した項目はサブエージェントで並列に行ってよいが、同じファイルを触る項目は同じエージェントか直列で扱う。
完了後、差分全体を確認し、plan にない変更が混ざっていないかを見る。

## 6. コミットと push

plan のコミット方針どおりにコミットする。fixup の場合は該当コミットに統合（autosquash）してから push する。履歴を書き換えた場合は `--force-with-lease` を使う。
コミットメッセージは PR の文脈なしで理解できる通常の内容にし、「レビュー対応」などの文言は入れない。

## やらないこと

- レビュアーへの返信、スレッドの resolve（明示指示がない限り）
- plan にない「ついで」の修正
